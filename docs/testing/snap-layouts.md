# Windows Snap：候选矩形与实际窗口

## 问题与修复

拖住窗口、在 Windows 顶部贴靠布局之间移动时，旧实现会在 `WM_MOVING` / `WM_SIZING` 中主动定位主窗及四个圆角层。即使系统只提供了尚未落地的拖动矩形，也会改变主窗、调整网页布局并重建裁剪区域。

v1.0.13 让系统提交主窗的位置和大小，圆角层跟随实际的移动和尺寸事件。圆角层使用 `UpdateLayeredWindow` 的仅位置更新，复用已有图像；没有新的位图、DC 或像素上传。设置面板也删除了主动定位主窗的拖动处理。

Microsoft 的消息合同说明：[WM_MOVING](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-moving)、[WM_SIZING](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-sizing)。仅位置更新的要求见 [UpdateLayeredWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-updatelayeredwindow)：源 DC、尺寸和混合参数为空，flags 为零。

## 自动回归

运行 `webview-host/tests/run-tests.ps1`。测试使用自己的 HWND 和隔离设置目录，不打开官网、不操作用户的聊天内容。

- 连续 60 个未提交的移动 / 大小候选：主窗、网页尺寸和四个圆角的位置保持不变，裁剪及像素更新计数不增加。
- 小于最小尺寸的候选：不提前改变真实窗口。
- 由原生 `SetWindowPos` 提交位置和大小后，四个圆角的真实 HWND 位置与主窗一致；仅保留首次四次图像上传。
- 已有检查继续覆盖默认与高 DPI、四角拉伸、真实系统尺寸循环、最小化恢复、置顶、设置及引导往返、快捷键和 GDI 资源。

## 现场验收

自动消息测试只证明窗口职责和更新行为。它不能替代 Windows 11 顶部 Snap Bar、DWM 缩略图以及实际官网内容在拖动时的帧率验收。

1. 打开已登录的小窗，输入一段未发送草稿。将窗口拖向屏幕顶部，保持按住鼠标。
2. 在左右半屏、三列和上下组合的候选之间多次来回移动，确认没有来回跳动、角层残留或白色裂缝。
3. 松手落入一个能容纳窗口的区域，再拖回普通窗口，确认草稿、登录状态及圆角保留。
4. 分别在置顶开关开启和关闭、不同显示缩放及多显示器上复测。检查任务栏恢复，以及设置和引导返回后的四角。

仍保持原有 360×480 DIP 最小尺寸；小于该尺寸的 Snap 区域不能容纳本工具，不应把它误记为已通过的布局。默认小窗尺寸及网页缩放不变。

## 性能证据边界

同一隔离主窗的改前 / 改后消息探针区分“候选但不提交”和“提交后实际重绘”。不将候选处理耗时写成真实官网帧率，也不使用之前其他窗口测试的毫秒数证明 Snap Bar 的流畅度。原生官网和人工拖动验收结果应单独记录。
